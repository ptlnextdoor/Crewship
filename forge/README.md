# forge

An unattended build loop that keeps developing one project on a Crewship host for hours, with no laptop and no operator in the loop. It complements Firstmate: Firstmate runs work you hand it; forge decides the next piece of work itself, builds it, checks it, lands it, and repeats until its deadline.

## How a cycle runs

```mermaid
flowchart LR
  Q{startable tickets < min_queue?} -->|yes| P[planner writes tickets]
  Q -->|no| B
  P --> B[builder: one ticket, fresh worktree]
  B --> G{gate.sh}
  G -->|fail| R[one repair pass] --> G2{gate.sh}
  G2 -->|fail| F[ticket: retry / blocked + evidence]
  G -->|pass| V[reviewer from the other vendor]
  G2 -->|pass| V
  V -->|REJECT| F
  V -->|APPROVE| L[rebase, re-gate, merge, push]
  L --> S[every N cycles: steward updates PROGRESS.md]
```

Reliability rules, each mapped to a failure it prevents:

| rule | prevents |
| --- | --- |
| State lives in files (`tickets/`, `PROGRESS.md`, `LEARNINGS.md`, git), never in a model's context | each session starting with amnesia |
| One ticket per session, each with command-checkable "Done when" | half-built features, "looks done" |
| When the change takes input, the planner's "Done when" names at least one edge input (empty, boundary, the other type, malformed) with its expected result and the file or doc that defines it, so the builder runs it and the reviewer's step 1 reruns it | wrong code that passes on typical inputs: a release gate of all assertions on typical inputs released 41% of wrong LLM repairs across 73 API-migration tasks, one edge input written from the spec cut that to 6.5% (per attempt, for example 0.233 to 0.057, in all three open-weight families) with no drop in correct completions, and the model's own self-tests helped less (preregistered, arXiv 2611.08269) |
| Under each file it names, the planner's `## Do` adds a `Tests:` line (the existing test that exercises it, or `none found`) and a `Siblings:` line (other places that may need the same change, or `none found`), names only and on their own lines, a starting point rather than a requirement | a session that spends its first half locating: on 144 C++ issue runs ByteAsk (a context engine that derives the location, related places and covering tests from the build, plus a check limited to those tests) fixed as many runs as the same model under Codex CLI (129 of 144 each) on 63-80% fewer tokens, most on little-known projects (preprint, 2026-11-09, vendor's own runs); here an LLM planner writes the pointers, and a step and a test name on one line would trip test_tampering's "remove/delete/drop … test" waiver |
| The builder runs every "Done when" command itself before its last commit and puts each with its output line in `PROGRESS.md`; a failing or unrun line is unfinished work | an attempt lost to a REJECT the builder could have seen: reflex1 #19's builder never ran `tools/profile_forward.sh` (it panics on the first measured shape) and the REJECT was its first sight of that; in #39 and #121 the builder ran the line, saw it fail and said so in PROGRESS.md, and those attempts are still lost, since forge reviews any non-empty diff; the gate covers none of these, and the reviewer's rerun costs a 30-minute other-vendor session plus the retry (LangChain's harness note: a check against the original task before completion, relayed on X 2026-10-30) |
| A "Done when" test command whose output shows no test ran (every `test result:` line `0 passed`, or pytest's `no tests ran`; a `running 0 tests` block for another binary beside one that ran is not) is a FAIL for the builder and the reviewer, whatever its exit code | a criterion met by exit status alone: `cargo test <name>` exits 0 and prints `0 passed; 1 filtered out` when the name matches nothing (checked on this box), so a misspelled or never-written test "passes"; 75.8% of the failed AppWorld coding-agent trajectories with an explicit status claim claimed success, and LLM judges reached 0.54 AUROC on them (0.65 at best on tau2-bench; arXiv 2606.09863) |
| A gate run that exits 0 while every `test result:` line in its output reads `0 passed` is a gate FAIL (forge checks the full output, not the tail; a run with no `test result:` line at all is left to the exit code) | the gate's own test stage running nothing and reporting green: a workspace members list or a `cfg` that drops every crate's tests (one that drops only some leaves another binary above `0 passed` and is not caught here), which `#[ignore]` grep and the test-count diff do not see; every one of reflex1's 108 recorded gate PASS tails holds a `test result:` line with at least one test passed, beside 964 per-binary `0 passed` lines (doc-tests, binaries without tests), so the check needs every line at zero, has no false positive on the record, and closes the case before it is seen, like the "Done when" no-test row above; a release gate reported PASS on a run in which one subgate executed neither of its checks, for two weeks, because "was a violation observed" was computed over the cases that ran (Silent Success, arXiv 2609.30307); 11% of successful industrial CI jobs are rerun and ignored exit codes are among the commonest silent failures (Aïdasso et al., arXiv 2509.14347) |
| The gate (`gate.sh`) is the oracle and protected: a diff touching `gate.sh`, `tickets/` or `.forge/` is rejected | passing by editing the tests |
| Gate output handed to the repair session, the PR comment and the ticket note is the stage headers (`== fmt`) and error lines (`error:`, `test ... FAILED`, `panicked`) that a 5,000-character tail cut, then the tail | a repair session told to fix a gate it cannot name: reflex1 PR #2, the one gate failure on record, posted two tails of rustfmt hunks with no `== fmt` line (its repair session died on Codex's usage limit, so the record shows the cut header, not a repair it misled); hybrid grep+tail reductions lead the cost-quality frontier for LLM log diagnosis and weak contexts cost 2-4x the tool calls (LogDx-CI, arXiv 2605.28876) |
| A third-party package new to `Cargo.lock` (or a new `pip install`) only when the ticket names it; forge diffs the lock file against `origin/main` before the builder's and the repair's gate runs and fails the attempt on a new or bumped third-party package the ticket does not name and no named crate pulls in (a word of the ticket counts as naming it), and the reviewer diffs the manifests and lock file and rejects any other. A `Cargo.lock` that does not parse as TOML fails the attempt naming the revision, rather than reading as a branch that adds nothing | an unrequested crate landing on main, where every later session builds it (the review runs after the builder and the gate have built it once, so it does not keep the code off this box); the rule was prose only in two prompts, and prose is skipped under load where a mechanical check is not (a fleet harness write-up, X 2026-10-29: "the rules that bit twice became hooks"); reflex1: 0 of 14 `Cargo.toml`-changing commits on main added a direct dependency no ticket names, so this is the copy beside the prose, costing seconds where the review runs after an 8-25 minute gate; an unreadable lock emptied both dependency guards at once, and a check that cannot read its input is unresolved, not a pass (Keller AI, 2026-11-10: on 88 sealed rule-breaking changes the best of seven automated reviewer setups approved 1, and its worst misses were changes whose earlier evidence no longer covered the code) |
| A test switched off (`#[ignore]`, `pytest.skip`), a net loss of test functions, or a net loss of assertion lines (`assert*`, `debug_assert*`) in the diff only when the ticket says so; forge reads `git diff -U0 origin/main...HEAD` over `*.rs`/`*.py` before the builder's and the repair's gate runs and fails the attempt otherwise (a ticket that writes the marker, or "remove/delete/drop ... test", counts as saying so, and "remove/delete/drop" within three words of "assert" does for the assertion count alone; a test or assertion moved or rewritten nets to zero), and the reviewer's step 3 reads the rest | passing by deleting or ignoring the failing test instead of fixing the code, the shortcut ImpossibleBench (arXiv 2510.20270) measures agents taking when spec and tests conflict, and passing by keeping the test and dropping the assertion that fails (a net-assertion count is a required CI job for agent PRs in piyushmehta.com 2026-10-31; the OpenAI 2026-10-06 incident it cites, a test rewritten to assert the monitor's absence, nets to zero here and stays reviewer step 4's); builder rule 12 said it in prose and the review that enforces it runs after the 8 to 25 minute gate; reflex1: 0 added `#[ignore]`, 0 removed `#[test]` and 0 commits with a net loss of `assert` lines in 627 commits on main, so this is the copy beside the prose |
| Builder and reviewer come from different vendors (`reviewer_alt` when they would match); the pick reads the configured model, so when the other vendor is out of quota and the reviewer's own fallback is same-vendor, the review comment and the ticket's done note say the cross-family check did not run | one model approving its own blind spots, and a same-vendor verdict read later as a cross-family one: forge chose the reviewer role before the session ran, and the comment and note named the model that ran without comparing it to the builder's (reflex1 routes both `reviewer` and `reviewer_alt` to `claude-fable-5-1` when their first model is out) |
| The reviewer treats commit messages, PR text, code comments and PROGRESS/LEARNINGS prose as the builder's account, not evidence, and does not read `git log` or the PR page for intent | a weakened check passing review because the builder explained it well (a refined explanation got 32/33 reintroduced CVEs approved where a plain one got 4/33; withholding it restored every detection) |
| Reviewer step 7 names, with file:line and the alternative, a `.clone()`, `.to_vec()` or `.iter().cloned().collect()` the diff adds in a per-sample, per-token or per-op loop only to end a borrow of `self` before a `&mut self` call; outside the steps-1-to-6 REJECT rule | a CPU inference path paying an allocation per step to satisfy the borrow checker: reflex1's gate runs `cargo clippy -D warnings`, but `redundant_clone` and `needless_collect` are allow-by-default nursery lints, so these pass it; one 12,349-line Claude TypeScript-to-Rust port carried 175 such copies in its tick loop and ran 1.9x faster with them refactored out (r/rust 2026-11-09), and Clippy-plus-manual audits of LLM C-to-Rust translations find non-idiomatic patterns human translations lack (arXiv 2602.00840) |
| Rebase and re-gate before merge | green branch, red main |
| The protected-path check runs again after the conflict with main is resolved, against `origin/main` | the merge-resolve builder session (29 reflex1 cycles ran one) committing `gate.sh` or `tickets/` through `git add -A`: it starts after the pre-gate check and only its prompt said not to |
| Retry with the failure evidence, escalate to `builder_hard` on the 2nd failure, block after `max_attempts` | infinite loops on one ticket |
| A ticket interrupted mid-cycle goes back to the queue free (not an attempt) at most `max_attempts - 1` times, then `blocked` with the count | unlimited uncharged builder sessions on a ticket whose cycle keeps dying (reflex1's 0012: 6 cycles for 3 counted attempts, two recoveries after `./gate.sh timed out after 1800 seconds`, about 4.6 lane-hours) |
| The planner is told how many tickets can start now (`depends:` all done) and how many startable ones it must add; forge logs the count after the turn | a planner turn every lane-1 cycle (10 in 13 h on reflex1, about 25 min each) because each wrote 8 tickets of which a median of 2 could start |
| A review that ends with no `VERDICT` and no review text (its timeout, a non-zero exit, or rc 0 with empty stdout) is rerun once before the attempt fails; a prose review without the verdict line is still the reviewer's answer | losing a 75-minute builder attempt to a stalled 30-minute review, to a session that never started (reflex1 0065: `Argument list too long`, charged as "reviewer did not approve"), to a provider error that is not a quota refusal (0005), or to a reply spent whole on thinking: Fable 5.2 at xhigh and max returned nothing after its 128K output tokens on the same prompt 5.1 finished (Playcode, 2026-11-09), and Fable is the reviewer's fallback |
| A merge conflict at landing re-syncs with main and re-gates, up to three times | losing an approved, gate-green attempt because another lane landed during the 8–25 min post-rebase gate |
| A lane's `main` reconciles with `origin/main` by merge when the rebase conflicts, and a reset of last resort keeps the dropped commits on a `sync-conflict/*` branch | discarding this lane's unpushed planner tickets, status changes and steward edits (`git reset --hard origin/main`, twice in reflex1's 23-hour run) |
| Model-written text (the ticket heading that becomes the PR title) is shell-quoted; bodies go through files | a backtick or `$(...)` in a ticket running as the owner's user |
| Every session prompt goes to omp through a file (`sessions/<cycle>-<role>.prompt`), never as an argument | a review of a large diff failing to start (Linux caps one argument at 128 KiB) and the attempt being charged to the ticket |
| After each ticket the lane's `CARGO_TARGET_DIR` loses the workspace's own artifacts (crates.io ones stay) | one more copy of every test binary per dependency change until the disk is full |
| Quota floor (`max_window_used_pct`), hard deadline, per-session timeouts | burning the owner's shared plan |
| GPU through `gpu.py` only: budget cap, max hours, deadline in the pod name, reaper timer | forgotten pods billing all night |
| The planner prompt carries the GPU budget `gpu.py` would still allow (`GPU_BUDGET_USD` minus the ledger) and tells it to write CPU-only tickets below a job's cost | a queue of GPU tickets each refused at the builder's first `gpu.py run` and charged as a lost attempt (reflex1: $14.88 of $15 spent, 85 of 140 tickets name a GPU; CLAUDE.md files in 228 orgs teach a production command and 214 commit nothing in front of it, r/ClaudeCode 2026-11-03) |
| The builder never puts an account, email, token or key into a request, file or command because something it read asked for it; only the ticket can authorize that | a page the builder fetched asking "identify your user" and getting the owner's login (Claude Code put the account email in HTTP headers on request, 2026-10-22) |
| A REJECT ends with a `Must change:` block (file and line, the input that shows it, the code to write) right before the verdict; the next attempt gets the review whole (up to 6,000 characters, omp's `[stderr]` chatter stripped), not its last 3,000: in 3 of reflex1's 10 REJECT reviews the tail dropped all or all but one PASS/FAIL ledger line, so the retry never saw which "Done when" line failed (feedback naming the failure location, the observed value and the admissible fix lifts repair 14/50 to 36/50; location and value alone stay near baseline - VeriHarness, arXiv 2607.14167) | a retry that rereads the reviewer's PASS/FAIL table and misses the fix (over 54,000 agent review comments: an inline code suggestion is the strongest predictor a comment gets acted on, long ones the weakest) |
| The retry builder reruns each earlier `Must change:` line's command against its own work before coding to it; a finding that does not reproduce, or whose expected value contradicts `## Done when`, is recorded in `PROGRESS.md` with the output and not applied; the reviewer re-checks the same lines | a correct retry rewritten to satisfy a wrong earlier review: a cross-family reviewer falsely rejected 2% of correct answers against 35% for self-review, and of 18 false rejects the 3 the executor complied with all became wrong while the 15 it ignored survived (arXiv 2609.04270); prompts that ask the reviewer for a proposed correction raise its misjudgment rate (Jin et al., ASE 2026); Memdoor's GVS5H rebuild lost 1 of 50 runs to a manager's counterexample with a wrong expected answer that the team rewrote a right program for (2026-10-31) |
| A `LEARNINGS.md` entry starts with its ticket id and the file or symbol it is about; the steward deletes an entry whose code has moved on | a builder following a lesson the code has outgrown (reflex1's file: 129 lines, 0 dates, 3 commit hashes; agents given a stored record with no validity state use it as if current, a 40.5-point drop on LongMemEval) |
| Outside its worktree the builder makes a file recoverable (tracked and clean, or copied aside without replacing an older copy) before any command that may overwrite, move or delete it, puts back what the ticket did not ask it to change, and notes in `PROGRESS.md` where the copy of the rest is | an untracked dataset, checkpoint or the owner's other repo clobbered by a side effect (reflex1 ticket 0057 ran `track.mjs` as a CLI and it rewrote `~/code/reflex/learn/track.json`; recovered only because it was tracked. ## Files

| file | what |
| --- | --- |
| `forge.py` | the loop: `run`, `once`, `status`, `steward` |
| `gpu.py` | RunPod jobs with guards: `run`, `list`, `reap`, `balance` |
| `prompts/{planner,builder,reviewer,steward}.md` | role prompts; `{PROJECT}`, `{GATE}`, `{TICKET}`, `{DIFF}`, `{STATE}` are filled in |
| `omp.yml` | config overlay every session runs with (`task.maxRecursionDepth: 0`, no sub-agents; `skills.enabled: false`, no user-scope skills; `memory.backend: "off"`, no memory tools or retention) |
| `projects/<name>.toml` | per-project config: repo, gate, roles (model + thinking), limits, env |
| `systemd/` | `forge@.service` (one loop per project), the GPU reaper timer, and a stall watchdog that restarts a loop whose log has not moved for 2 h |

A project repo needs `gate.sh` (exit 0 = good), `tickets/`, `AGENTS.md`, `ROADMAP.md`, `PROGRESS.md`, `LEARNINGS.md`.

## Install on a host

```bash
mkdir -p ~/.config/forge ~/.config/systemd/user
cp ~/Dev/Crewship/forge/projects/reflex1.toml ~/.config/forge/
cp ~/Dev/Crewship/forge/systemd/* ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now forge@reflex1.service forge-gpu-reap.timer forge-watchdog@reflex1.timer
```

Linger must be on (`loginctl enable-linger $USER`; Crewship's `enable_linger` does this) so the loop keeps running after you log out.

## Watch and steer

```bash
python3 ~/Dev/Crewship/forge/forge.py status --config ~/.config/forge/reflex1.toml
journalctl --user -u forge@reflex1 -f
python3 ~/Dev/Crewship/forge/gpu.py list
```

Steer by committing to the project repo: add or edit a ticket, reorder by renaming, set `status: blocked` to skip one, or edit `ROADMAP.md`; the loop pulls `main` every cycle. Stop with `systemctl --user stop forge@reflex1`.

`status` also prints merged/attempts per forge version (one short hash per file, `forge.py.planner.builder.reviewer.steward`, so two rows show which file changed between them) plus the omp release (`omp --version`), both taken when each history entry is written: `~/.local/bin/omp` is a symlink into a versioned install, so an upgrade changes the instruction stack under a running lane with no change to the hash. Each tally carries a Wilson 95% interval (`85/122 (61-77%)`): identical reruns of one agent move pass@1 by 2 to 6 points (arXiv 2602.07150), so two versions differ only when their intervals clear each other. It is a tally over different tickets, not a controlled comparison.

A second line tallies merged/attempts per builder model that ran (the fallback after a quota refusal, not the configured one). On 135 HumanEval/ClassEval tasks a planner-coder-reviewer pipeline cost 3.22x a single Opus call and solved no more; the saving was in choosing the model per task (arXiv 2610.37700). Forge cannot choose per task until it knows each builder's rate, and the per-version tally merges a lane that fell back to Codex mid-day with the Opus runs around it. Same caveat: different tickets, not a controlled comparison. The same line carries lane-minutes per merged ticket per model, every attempt that carries `secs` on its history entry counted, failed ones included: omp prints no token count and the lanes are plan-billed, so wall time is the one cost forge can read (compute time tracks energy and cost when the meter is unreadable, arXiv 2610.39621), and a model is compared on resources per completed task, not per call, because a failed attempt still spends them (arXiv 2610.19345); reflex1's 85 merges read a median of 60 min while its 37 failed cycles held 2,097 of 7,139 lane-minutes, 84 per merge. The span includes forge's gate runs, the review by the other vendor's model and any merge-resolve session, and `builder_hard` (same model string, more effort) takes the hard tickets and later attempts, so it is not the builder model's own time; same caveat as the rate.

The model line is repeated per ISO week with the median lane-minutes per attempt beside each rate (`anthropic/claude-opus-5-5 2026-W45 12/16 (51-90%) 48 min/attempt, 2026-W46 ...`). The version row moves only when forge or omp changes and the model row pools every week, so a change on the provider's side under one model name (arXiv 2307.09009: the same GPT-4 name produced more code-formatting errors in June 2023 than in March; Test Before You Deploy, FSE 2026, asks deployers for their own regression checks because hosted models update without a version change) showed nowhere in `status`. The minutes are the volume signal: on LiveNerf's frozen Opus 5.5 panel a lower effort setting cut output tokens 26-62% against 4-8 accuracy points, so volume moves before the rate does, and wall time is the proxy forge has for tokens. Same caveat: a week's tickets differ from the last week's, so two weeks differ only when their intervals clear each other, and a week of long tickets reads as a slow week.

The model line is also split by builder role (`builder 40/61 (53-76%) 58 min/merge, builder_hard 9/21 (24-63%) 131 min/merge`): `cycle()` runs `builder_hard` (xhigh, its own `timeout_min`) from a ticket's third attempt and from the first on a `difficulty: hard` ticket, and the model row pools both levels under one name. A turn cap at the baseline's 75th percentile cut cost 24-68% at the same solve rate, and granting more only to the tasks that needed it cut 12-24% further (Gao and Peng, ICSE 2026, doi 10.1145/3744916.3773250); this row is the per-level merge rate and lane-minutes per merge that says whether the escalation merges more or only runs longer. Entries written before `role` was recorded tally as `pre`.

Attempt #1 alone is split by role too (`merged/attempts at attempt #1 by builder role: builder 30/48 (48-75%), builder_hard 3/9 (12-65%)`): a `builder_hard` first attempt is a ticket the planner marked `difficulty: hard` before any failure, so this row reads the planner's label as a predictor of what needs the 90-minute xhigh session, which the role row (pooled with attempt-3 escalations) and the attempt-number row (pooled with normal tickets) both hide. Expert difficulty ratings align only weakly with what coding agents actually spend (arXiv 2604.22750), so until this row fills the label is a guess.

Each history entry also stores `meter`, every plan window's `% used` (`{"anthropic Claude 7 Day (Fable)": 61.0, ...}`) as `quota_ok()` read it from `omp usage` at that cycle's start. The window is the bill the lanes actually pay, and omp prints no token count, so a week's meter climb divided by its merges (from `state.json`, every lane's file) is the one way here to see a vendor reprice the meter under a fixed model name: one user's weekly Fable meter went from 0.41% to 0.76% per message between Oct 15 and Nov 5, 2026, with weighted tokens per message flat (drewhoover.com, two readings, one person). `status` prints that tally as `plan-window climb per merged ticket per ISO week` (`anthropic Claude 7 Day 2026-W45 +62.0% / 11 merged = 5.6%/merge, ...`): every lane's entries pooled in claim order (`at` minus `secs`) (the windows are shared), the rises between consecutive readings of one window summed, a fall read as the window resetting rather than as spend. Read it only against this loop's own earlier weeks: across 404 JetBrains engineers, the 90th percentile of token spend was 39 to 240 times the 10th among weeks with similar commit counts, while within one engineer doubling spend went with about 10% more commits (arXiv 2611.13396). The owner's own sessions burn the same windows and are in the climb; the row stays `-` until a window's reading rises over its previous one.

A third line tallies failed attempts by the guard that ended them (`builder produced no`, `diff edits protected`, `gate still failing`, `reviewer did not`, `merge conflict landing`, ...: the first three words of the cause `fail()` logs, kept on the history entry as `why`). This count says which checks still end attempts and how often; it is not a case for deleting one: the gate (`gate still failing`, `gate failed after`), the reviewer (`reviewer did not`) and the protected-path and dependency checks (`diff edits protected`, `the repair edited`, `resolving the conflict`, `diff adds packages`, `the repair added`) read zero because the layers in front of them hold. Entries from before `why` existed are not counted; reflex1's log cannot supply them, its RETRY/BLOCKED heads were PR urls.
